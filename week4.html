Format Strings & Memory Safety

How format string vulnerabilities allow attackers to read and write arbitrary memory, the concepts of spatial and temporal memory safety, and command injection attacks.

Format String Vulnerabilities

What Causes a Format String Vulnerability?

Passing user-controlled input directly as the format string to functions like printf(), fprintf(), or sprintf().

🔴 Dangerous

printf(buf);
// User controls format string!

🟢 Safe

printf("%s", buf);
// buf treated as data only
🔓

Format String Exploits

Key Format Specifiers for Attacks

SpecifierActionSecurity Impact
%xReads 4 bytes from stack as hexStack data leakage
%nWrites number of chars printed to addressArbitrary memory write
%sReads string from pointer on stackMemory read

Leaking Stack Data

By printing many %x specifiers, attackers can dump successive stack values — revealing local variables, saved registers, return addresses, and even canary values.

// Attacker input: "%x %x %x %x %x %x"
// Output: bffff7a0 0 b7e5e224 b7fd7ff4 bffff7a8 0804849e
//         ↑ leaked stack data including addresses

Writing to Memory with %n

The %n specifier writes the count of characters printed so far to a memory address. Using padding like %1000x lets attackers control the exact value written — achieving arbitrary memory writes.

Critical: With %n, attackers can overwrite return addresses, GOT entries, or function pointers to hijack execution.
🔒

Memory Safety

Two Types of Memory Safety

📐 Spatial Safety

Ensuring accesses stay within allocated bounds. Violations: buffer overflows, out-of-bounds reads.

⏱️ Temporal Safety

Ensuring memory is accessed only while still allocated. Violations: use-after-free, dangling pointers.

Use-After-Free

Accessing memory after it has been freed. The memory may have been reallocated for a different purpose, leading to data corruption or code execution.

Why C Is Not Memory Safe

C lacks automatic bounds checking and safe memory management. The programmer is fully responsible for ensuring all memory accesses are valid — and humans make mistakes.

Integer Overflow → Buffer Overflow

Overflowed size calculations may allocate too little memory, causing later writes to overflow the undersized buffer.

// If size overflows to a small value:
int size = user_input + header_len;  // overflow!
char *buf = malloc(size);            // tiny allocation
memcpy(buf, data, user_input);       // massive overflow

Memory Safety vs Type Safety

ConceptWhat It Ensures
Type SafetyPrevents incorrect type interpretation
Memory SafetyEnsures valid bounds and lifetime of accesses

Command Injection

Why system() with User Input Is Dangerous

system("time ./" + user_input);
// If user_input = "prog; rm -rf /"
// Executes: time ./prog; rm -rf /

Attackers inject shell commands using metacharacters like ;, |, &&, or backticks.

Prevention

  • Use exec functions instead of shell commands (no shell interpretation)
  • Sanitize dangerous characters from input
  • Use allowlists — only accept known-safe input values
✅

Mitigations

Safe printf Usage

Always use a format string literal and pass user input as an argument:

printf("%s", user_input);  // ✅ SAFE — input is data
printf(user_input);         // ❌ DANGEROUS — input is code
Core Principle: Never treat untrusted input as executable code. This principle applies to buffer overflows, format strings, SQLi, and all injection attacks.
