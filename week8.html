Security Testing

Functional Testing vs Security Testing

✅ Functional Testing

Checks whether software behaves correctly for legitimate inputs and use cases.

🔴 Security Testing

Checks whether the program can enter a dangerous state — crashes, memory corruption, code execution, data leaks.

Three Levels of Security Testing

  1. Risk-based security testing — prioritise testing based on risk assessment
  2. Source code review (White-box) — examine code with full access to source
  3. Fuzz testing / Penetration testing (Black-box) — test from outside without source access
📖

Source Code Review

Common Issues Found

  • Hardcoded passwords/keys — credentials embedded in source code
  • Improper input validation — missing or insufficient checks
  • Dangerous functions — use of strcpy(), gets(), sprintf()
  • Resource leaks — unclosed files, sockets, or memory
  • Memory safety issues — buffer overflows, use-after-free
🔍

Static Analysis (SAST)

What Is SAST?

Static Analysis Security Testing analyses source code without executing the program to detect potential security vulnerabilities. Tools scan for known dangerous patterns, unsafe function calls, and potential data flow issues.

Advantages

  • Quickly find common vulnerabilities at scale
  • Automate repetitive analysis tasks
  • Help developers focus on the riskiest code sections
  • Can be integrated into CI/CD pipelines

False Positives & False Negatives

🟡 False Positive

Tool reports a vulnerability that is not actually a bug. Wastes developer time investigating non-issues.

🔴 False Negative

Tool misses a real vulnerability. Creates a false sense of security. More dangerous.

Limitations of SAST

  • Cannot detect all vulnerabilities (no tool is perfect)
  • Miss design-level flaws and business logic errors
  • Depend on predefined rules — novel attacks may be missed
  • Can produce many false positives, causing alert fatigue
Key Takeaway: SAST is a valuable tool but must be combined with other testing approaches (dynamic analysis, manual review) for comprehensive coverage.
📊

Control Flow Graphs

What Is a CFG?

A Control Flow Graph represents the possible execution paths in a program. Nodes are basic blocks (sequences of instructions with no branches), and edges represent possible control flow transitions between them.

CFGs are used by compilers for optimisation, by static analysis tools for vulnerability detection, and by CFI for runtime protection.

🔐

Control Flow Integrity

What Is CFI?

A security defence ensuring a program only follows valid execution paths defined by its Control Flow Graph. Any attempt to deviate from the expected control flow is detected and the program is terminated.

How CFI Prevents Attacks

CFI checks indirect jumps and calls at runtime. If execution attempts to follow an invalid control-flow path, the program aborts. This prevents:

  • ROP attacks — chained gadgets violate expected control flow
  • Return-to-libc — unexpected function calls detected
  • Shellcode execution — jumping to injected code is not in the CFG
Why It's Effective: Unlike ASLR or canaries, CFI provides a principled defence based on program semantics rather than randomisation.
