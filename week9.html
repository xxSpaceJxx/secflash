DAST vs SAST

Static vs Dynamic Analysis

📄 Static Analysis (SAST)

Examines source code without running the program. Finds issues like unsafe function calls, hardcoded secrets, and code patterns.

▶️ Dynamic Analysis (DAST)

Tests the program while it is running. Finds crashes, race conditions, memory errors, and runtime logic flaws.

Why Both Are Needed

Dynamic analysis finds vulnerabilities that only appear during execution — runtime behaviour, timing-dependent bugs, and real-world interaction patterns that static analysis cannot observe.

Complementary: SAST catches code-level issues early; DAST catches runtime issues late. Use both for comprehensive coverage.
🎯

Penetration Testing

What Is Penetration Testing?

A security testing approach that simulates real-world attacks against a system to identify vulnerabilities that an attacker could exploit. Testers think and act like adversaries.

Functional Testing vs Penetration Testing

AspectFunctional TestingPenetration Testing
PerspectiveLegitimate userAttacker
GoalVerify correct behaviourFind exploitable weaknesses
InputsValid, expectedMalicious, unexpected
SuccessSystem works correctlySystem is compromised

Limitations

Penetration testing does not prove a system is secure. Failing to find vulnerabilities only proves that none were found under those specific test conditions. It does not guarantee that no vulnerabilities exist.

Remember: "Absence of evidence is not evidence of absence." A clean pen test report means no bugs were found — not that none exist.
🎲

Fuzz Testing

What Is Fuzzing?

An automated testing technique that sends unexpected, malformed, or random inputs to a program to discover crashes, hangs, or vulnerabilities. It's highly effective at finding edge-case bugs that manual testing misses.

The 6 Steps of Fuzz Testing

  1. Identify the target system — what program to test
  2. Identify inputs — files, network data, API calls
  3. Generate fuzz data — create malformed inputs
  4. Execute tests — feed inputs to the program
  5. Monitor behaviour — watch for crashes, hangs, errors
  6. Log defects — record inputs that trigger bugs

Mutation-Based vs Generation-Based

🔄 Mutation-Based

Modifies existing valid inputs by flipping bits, inserting random data, or truncating. Easy to set up but may miss deeply structured inputs.

🏗️ Generation-Based

Creates inputs from specification rules (protocol definitions, grammars). More thorough but requires knowledge of the input format.

What Fuzzing Can Detect

  • Segmentation faults — invalid memory access
  • Use-after-free — accessing freed memory
  • Null pointer dereference — accessing address 0
  • Race conditions — timing-dependent bugs
  • Infinite loops / hangs — program stops responding
🧬

Advanced Fuzzing

Coverage-Guided Fuzzing (Grey-Box / White-Box)

Uses instrumentation to observe which program paths are executed during each test. The fuzzer then generates inputs that explore new code paths instead of repeating the same ones.

Key Advantage: Coverage-guided fuzzers like AFL and libFuzzer can systematically explore deep program logic that random fuzzing would take exponentially longer to reach.

Security Testing Plans

What Is a Security Testing Plan?

A formal document describing:

  • What will be tested (scope, targets)
  • Why (risk assessment, business requirements)
  • How (methodology, tools, techniques)
  • When (timeline, milestones)
  • Who is responsible for each testing activity
🔲

Pattern-Based Testing

Input Validation Vulnerability Test Pattern

A structured approach to testing input handling. Targets vulnerabilities caused by insufficient input validation:

  • SQL Injection — injecting SQL through form fields
  • Path Traversal — accessing files outside intended directories (e.g., ../../etc/passwd)
  • PHP File Inclusion — including remote or local files through parameters
